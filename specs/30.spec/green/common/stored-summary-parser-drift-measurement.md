# 파서 계약이 바뀌면 저장된 요약이 낡는다 — 그 낡음은 측정된다

> **위치**: `src/Log/api.ts` — `trimmedContents` (`:77`, `BLOCK_TAGS` `:59`) · 쓰기 경로 `postLog`(`:96`) · `putLog`(`:114`). 소비 표면: `src/Log/LogList.tsx:277-278` · `src/Search/Search.tsx:230`. 발화 채널: **현재 부재** (`check:*` 17건 중 0).
> **관련 요구사항**: REQ-20260831-073 FR-01~FR-06 · NFR-01~NFR-04 (출처: 운영자 결함 신고 `20260831-0934-stored-summary-frozen-at-old-parser.md`)

## 역할

`markdownToHtml` 산출 계약을 바꾸는 변경은 **그 변경이 `trimmedContents` 산출에 미치는 영향을 측정한 결과**를 남긴다. 영향이 있으면 갈라진 입력 부류를, 없으면 `영향 0` 을 박제한다. **침묵은 미측정과 구분되지 않으므로 침묵을 허용하지 않는다.**

**방어 대상 (사용자 관측 표면 — `RULE-07 §주제 우선순위 1`)**: 목록(`LogList.tsx:277-278`)과 검색 미리보기(`Search.tsx:230`)가 그리는 것은 본문이 아니라 **저장 시점에 계산돼 서버에 박힌 요약**이다. 요약은 `trimmedContents` 를 거치고 그 함수는 `markdownToHtml` 을 통과시킨다. 따라서 **파서 계약을 고치면 그날 이후 저장분만 새 규칙을 따르고 이미 저장된 글의 요약은 옛 규칙에 얼어 있다.** 독자는 목록에서 `오늘 배운 것 ##` 을, 본문에서 `오늘 배운 것` 을 본다.

**회복은 이 계약의 대상이 아니다** (저장소 밖 · 1회성). 계약이 되는 것은 **결합 자체**다 — 파서 산출 변경이 저장된 파생 데이터를 낡게 만든다는 사실은 저장소 안에 있고 **반복된다.**

**의도적으로 하지 않는 것**:

- **회복** — 글별 재저장 · 서버측 일괄 재계산 · 방치 판단. 운영 결정이며 1회성이다.
- **렌더 시점 재계산** — 목록 응답에 원문 마크다운이 없다 (`LogList.tsx:10-12` 주석과 타입: 평탄화된 최신 리비전이고 `contents` 는 이미 절단된 평문이다). 재론하려면 서버 응답 형상 변경이 선행한다.
- 요약 길이·말줄임 정책, `BLOCK_TAGS` 완전성(`summary-block-boundary-tag-derivation` 소유), 엔티티 복원 규칙(`decodeEntities`).

## 공개 인터페이스

- `trimmedContents(contents: string): string` — **시그니처·동작 무변경**. 본 계약은 이 함수를 고치지 않는다.
- 신규 측정 채널 1건. 형태는 지정하지 않는다 (`check:*` 스크립트 · task DoD 절차 · 게이트 테스트 중 어디든).

## 동작

1. **(I1) 요약 영향은 두 리비전 비교로 잰다** (FR-03): 판정 대상은 단일 HEAD 에서 요약 산출이 *"옳은가"* 가 아니라 **변경 전후 산출의 차집합**이다. 옳음의 기준이 곧 파서 계약이므로 단일 리비전 판정은 항진명제가 된다.

2. **(I2) 측정 입력은 열거하지 않고 도출한다** (FR-02): 입력 집합은 **해당 축의 게이트 픽스처에서 도출**한다. 고정 입력 목록을 새로 박아 넣는 것은 같은 결함을 한 겹 옮기는 것이다 — 오늘 축이 갈라진 것을 아무도 몰랐던 이유는 열거 부재가 아니라 **측정 자체의 부재**였다.

3. **(I3) 영향 0 은 침묵과 구별된다** (FR-01): 측정이 수행됐고 차이가 없다는 것과 측정이 수행되지 않았다는 것이 서로 다른 산출을 낸다. 입력 도출이 공집합이면 통과가 아니라 **무판정 실패**다.

4. **(I4) 갈라진 부류는 사용자 관측 표면의 언어로 기록된다** (FR-04): *"목록·검색에서 기존 글이 무엇으로 보이는가"*. `TSK-20260831-13-b` 가 이미 그 언어를 갖고 있었으나 §배경 산문에만 있었고 `## 검증/DoD` 에는 없었다 — 그래서 회수 문서에 남지 않았다.

5. **(I5) 같은 함수가 두 시점에 계산돼 서로 다른 신선도로 화면에 닿는다** (판정된 현행): `trimmedContents` 는 **저장 시점**(`postLog` · `putLog` → 서버 `summary` 필드 → `LogList`·`Search` 가 그린다)과 **렌더 시점**(`LogSingle.tsx:81` → `meta description`) 양쪽에서 돈다. 앞쪽은 저장 당시 파서에 얼어 있고 뒤쪽은 언제나 최신이다. **따라서 같은 글의 목록 요약과 `meta description` 이 서로 다를 수 있다** — 그 갈림이 이 계약의 존재 이유이며 판정면이다. 두 경로가 같은 시점에 계산된다면 이 축은 열리지 않는다.

   > **req 문면 정정.** REQ-073 §배경 (1) 은 *"쓰기 경로에서만 계산된다. 읽기 경로에는 요약을 만드는 코드가 없다"* 고 적었다. **목록 축에서는 참이고 전체로는 거짓이다** — `LogSingle.tsx:81` 이 렌더 시점에 같은 함수를 부른다 (본 흡수 재실측: 비-테스트·비-fixture hit **5**, req 는 3으로 봤다). 목록 응답에 원문이 없다는 §배경 (2) 의 판정은 그대로 유효하다(`LogList` 는 재계산할 재료가 없다) — 단일 글 화면은 원문을 받으므로 재계산이 가능했던 것이고, **그 비대칭이 바로 낡음이 목록에서만 보이는 이유**다. 이 정정은 결합을 약화시키지 않고 관측 표면을 하나 더 준다.

### 왜 두 리비전인가 (설계 지점)

**단일 HEAD 에서는 잴 것이 없다.** `trimmedContents(x)` 의 "옳은" 값은 그 HEAD 의 파서가 내는 값이고, 그것은 정의상 항상 일치한다. 낡음은 **저장 시점의 파서**와 **현재의 파서** 사이에 있으므로, 저장소가 잴 수 있는 근사는 **두 리비전의 산출 차이**다. 그 차이가 곧 *"그 사이에 저장된 글의 요약이 지금 규칙과 어긋난 부류"* 다.

## 회귀 중점

- **고정 입력 6건을 새로 박는 방향은 다음 축에서 되풀이된다.** 오늘 갈라진 축은 3개였는데 이 tick 안에 4개가 됐다 (§스코프 규칙 실측). 열거는 그날의 축만 덮는다.
- **단일 HEAD 판정으로 바꾸는 방향은 항진명제를 만든다.** 항상 rc=0 이고 아무것도 붙들지 않는다.
- **`trimmedContents` 를 고쳐 차이를 없애는 방향은 계약을 오해한 것이다.** 차이는 결함이 아니라 **파서 계약이 의도대로 착지한 결과**다. 재는 것은 그 사실이 기록되는가이지 차이가 0인가가 아니다.
- **본문 렌더 게이트로 대신하는 방향은 (I5) 를 놓친다.** 본문은 매번 다시 그려지므로 언제나 최신이다. 낡는 것은 요약뿐이다.
- **회복을 계약에 넣는 방향은 범위를 넘는다** (FR-06 Won't).

## 참고

### 채널 부착 선행 (`RULE-07 §promote 조건 4`)

Must 측정 게이트를 선언하는데 발화 채널 실경로가 **0건**이다 (`check:*` 17건 중 0 · 요약 산출을 재는 테스트 0). 채널 부착 task 가 선행 조건이다.

채널 형태를 지정하지 않은 이유는 **비용 구조가 다른 두 갈래가 다 성립하기 때문**이다 — (a) `check:*` 스크립트가 두 리비전을 `git archive` 로 떠서 비교(무겁지만 자동), (b) 파서 계약을 바꾸는 task 의 DoD 절차로 못 박음(가볍지만 발행자 의존). **(b) 를 고르면 `RULE-06` 의 task DoD 규약과 맞물리므로 그쪽 문면 개정이 필요할 수 있고 그것은 운영자 소관이다.**

### 미측정·비판정 항목 (`RULE-07 §수용 기준 문장 규약`)

- **이미 저장된 글이 실제로 몇 건 낡았는가** 는 측정 채널이 없다. 서버 데이터이며 저장소 밖이다.
- **회복 경로**(글을 한 번 수정하면 `putLog` 가 요약을 다시 만들어 그 글은 낫는다)는 참이지만 **어느 계약도 소유하지 않는다**. 전면 회복은 운영자 결정이다.
- **두 리비전의 선택 기준**(무엇과 무엇을 비교할 것인가)은 채널 설계 시점의 판단이다. 본 흡수는 `19d70a9`(오늘 첫 파서 수정 직전)를 썼으나 그것은 예시이지 계약이 아니다.
- **더 오래된 축**: 꺾쇠 삭제(`List<String>` → `List`)는 `df2b7ff`(2026-08-29)·`8f0d589`(2026-08-30)가 고쳤고 **오늘 축보다 이틀 더 오래** 저장 데이터에 쌓였다. 두 리비전 비교로는 그 축이 보이지 않는다(양쪽 다 이미 고쳐진 상태) — **비교 구간 밖의 표류는 이 계약이 잡지 못한다**는 한계를 여기 적는다.
